# Sync review: real bugs, most severe first

I found no bug that corrupts the merge itself (for the two-device case, `merge`/`mergeById` really are symmetric, and `downloadNew`'s ordering does converge — I traced both orderings of `legacy` vs a device file and they agree). What I did find is one **unguarded destructive write that loses a concurrent edit**, several paths that **resurrect deleted content**, and a set of robustness/convergence holes.

---

## 1. Purge of a note "deleted elsewhere" uses a stale `dirty` flag → loses a concurrent edit, no CAS guard

**Where:** `SyncEngine.sync()` / `SyncEngine.syncNote()`

```kotlin
val localNotes = store.notesForSync()          // snapshot taken ONCE
...
runCatching { syncNote(note, cloudNotes[note.id]) }   // per note, seconds later
```
```kotlin
files == null && wasSynced(note) && !note.dirty -> {
    // Deleted on another device, and not edited here since.
    store.purge(note.id)
    deletedHere++
}
```

Every other destructive write in `settle` is guarded (`store.replaceIfUnchanged(result, note.updatedAt, …)`); this one is not. `note.dirty` is the value read at the start of the sync, and the loop over `localNotes` can take a long time (it downloads and decodes peers).

**Concrete sequence**
1. Note N is synced and clean (`dirty = 0`). Another device deletes N; its files are removed from the cloud.
2. Sync starts: `notesForSync()` reads N with `dirty = 0`.
3. While the loop is busy with other notes, the user drags N into a folder → `NoteDao.moveToFolder` → `dirty = 1, updatedAt = now`. (Same for `setLocked`, `moveToTrash`, or an inbox photo placed by `fillPhotoRequest`, which are not protected by `markOpen`.)
4. Sync reaches N: `files == null && wasSynced(note) && !note.dirty` — the stale `false` → `store.purge(note.id)`.

**What goes wrong:** the note is deleted locally *and* the user's just-made edit is gone, although the code's explicit rule is "deleted elsewhere but edited here: the edit wins and it uploads again" (`files == null -> if (upload(note, remoteId = null)) uploaded++`). Since `files == null` means the cloud copy is gone too, there is no copy left to recover from.

**Confidence:** high that the code has no guard; medium that users hit it (needs a delete on another device plus a non-editor mutation during a sync).

**Fix:** make the purge conditional on the row still being clean, e.g. a DAO call
`@Query("UPDATE notes SET deleted = 1, dirty = 1 WHERE id = :id AND dirty = 0 AND updatedAt = :expected")`
and only call `store.purge` when it returns 1; if it returns 0, treat the note as "edited here" and fall through to `upload`.

## 2. `NoteRepository.delete()` decides from a possibly stale `Note` → a deleted note comes back

**Where:** `NoteRepository.delete`

```kotlin
suspend fun delete(note: Note) {
    if (!note.isInCloud) purge(note.id) else dao.markDeleted(note.id, System.currentTimeMillis())
}
```

`isInCloud` is `remoteId != null || lastSyncedAt != null`, evaluated on the object the UI passed in (from `observeAll()`).

**Concrete sequence**
1. The user creates note N (never synced: `remoteId == null`, `lastSyncedAt == null`) and the notes list holds that stale object.
2. Sync runs and uploads N; `markSynced` sets `driveFileId`, `remoteVersion`, `lastSyncedAt`.
3. The user deletes N from the still-displayed list → `isInCloud` is false on the stale object → `purge(N)` (row, ink and attachments deleted, **no tombstone**).
4. Next sync: `cloudNotes` contains N (the cloud files are still there), `localIds` does not → `downloadNew(N, files)` → the note reappears, minus anything that was only local.

**What goes wrong:** a deleted note silently returns (and, if `insertFromCloud`/`ink.save` had already deleted the files, it returns with the cloud's older content).

**Confidence:** high on the mechanism, low–medium on frequency.

**Fix:** decide inside a transaction / query, e.g. `@Query("SELECT driveFileId IS NULL AND lastSyncedAt IS NULL FROM notes WHERE id = :id")` and act on that; or always write a tombstone and let `syncNote` purge it when `files == null && !dirty`.

## 3. Upgrade path: a legacy note with `remoteVersion == null` gets a `null` base → deletions by other devices are permanently undone

**Where:** `SyncEngine.changedPeers`

```kotlin
val legacy = files.peers[NoteFile.LEGACY_DEVICE]
if (legacy != null && LEGACY_DEVICE !in seen && note.remoteId == legacy.id && note.remoteVersion != null) {
    val snapshot = store.syncedSnapshot(note)
    if (snapshot.isNotEmpty()) { store.savePeer(...); seen[LEGACY_DEVICE] = note.remoteVersion }
}
```

The base for the legacy file is only recorded when `remoteVersion != null`. On a DB migrated from the old format that column can still be `null` (it is new; the old app never set it), and a note downloaded by the old app also has it `null`.

**Concrete sequence**
1. A upgrades, deletes stroke S5 from N, uploads `N.A.4enote` with `seen = {legacy: v0}`. The legacy file `N.4enote` (still containing S5) is never rewritten or removed.
2. B upgrades. B's N has `remoteId == legacy.id` but `remoteVersion == null` → the block above does nothing, `seen[legacy]` stays unset.
3. B merges A's file with base `null` (no source in `commonBase`): `mergeById` with an empty base keeps **everything** → S5 is back in B.
4. B uploads `N.B.4enote` containing S5 again. A merges it: base = legacy (which has S5) and S5 is in B's file → `keptLocal`/`keptRemote` keep it → **S5 is alive on every device again, permanently.**

**Confidence:** medium (needs the `null` `remoteVersion` state to still exist at the first post-upgrade merge).

**Fix:** treat the legacy file as *already seen* whenever `note.remoteId == legacy.id` and the note was synced (`note.remoteVersion ?: note.lastSyncedAt`); if there is no recorded version, record the snapshot from the local note itself as the base for `LEGACY_DEVICE` rather than falling back to `null`.

## 4. `replaceIfUnchanged` commits the DB row before the ink, and the ink is written from a pre-guard read → a concurrent ink save is reverted

**Where:** `NoteRepository.replaceIfUnchanged` together with `NoteRepository.saveDocument`

```kotlin
val replaced = dao.replaceContentIfUnchanged(..., expectedUpdatedAt = expectedUpdatedAt, ...) > 0
if (replaced) {
    seal(note.id, note.locked)
    ink.save(note.id, InkSerializer.decode(note.inkData))   // ink from a read taken BEFORE the guard
```
```kotlin
suspend fun saveDocument(noteId: String, title: String, doc: InkDocument) {
    ink.save(noteId, doc)                                   // (a)
    if (dao.markEdited(noteId, title, System.currentTimeMillis()) == 0) { ... }  // (b)
}
```

The `updatedAt` guard protects the *row*, but the *ink* is written from `store.withContent(note)` taken before the guard, and `saveDocument` writes the ink (a) before stamping `updatedAt` (b). Any writer that is not in `openNotes` (the inbox photo fill on a note the UI does not consider open, a save issued after `markClosed`, `placeInboxScans` from another entry point) can be interleaved as:

1. Sync: `store.withContent(note)` reads the ink at T0.
2. Editor/other writer: `ink.save(newDoc)` at T1 (inside `saveDocument`, step (a)).
3. Sync: `replaceContentIfUnchanged` at T2 — `updatedAt` still equals `expectedUpdatedAt`, because `markEdited` (step (b)) has not run → **matches**.
4. Sync: `ink.save(note.id, decode(result.inkData))` — overwrites the files with the T0 content. The strokes saved at T1 are gone from disk.

The DB row is left clean, so nothing ever uploads or repairs the loss; only a later full re-save by the editor would.

**Confidence:** high that there is no lock protecting the (read ink → CAS row → write ink) sequence; medium-low that the interleaving is reachable from the UI (`markOpen`/`markClosed` are called by the editor, so a save that lands after `markClosed` is the realistic trigger).

**Fix:** either (a) stamp `updatedAt`/`dirty` *before* writing the ink and have sync skip notes with a pending editor save, or (b) hold the note's mutex across the CAS + `ink.save`, and re-check `store.isOpen(noteId)` immediately before writing the ink (abandon the merge if it became open).

## 5. After a merge upload fails, a clean note's own cloud file is stale forever

**Where:** `SyncEngine.settle`

```kotlin
if (changed.isEmpty()) {
    val catchUp = own != null && ((pdfExporter != null && note.remotePdfId == null && !note.locked) || needsSealing(note, own))
    if ((note.dirty || catchUp) && upload(note, own?.id)) uploaded++
    return
}
```

The `behind` check (`own.version != note.remoteVersion`, `!sameContent(syncedSnapshot, result)`) only runs in the *changed* branch. If `settle` stored the merge (`replaceIfUnchanged` → ok, `savePeer` → ok) and then `upload` threw, or the process died before `markSynced`, the peers are already recorded and the note is clean.

**Concrete sequence:** A merges B's file, `replaceIfUnchanged` ok, `savePeer` ok, `provider.upload` throws (network) → `runCatching` records an error. Next sync: `changedPeers` is empty (peer version recorded), `note.dirty` is false, `catchUp` false → no upload, forever. A's cloud file never gets the merged content and `remoteVersion` stays stale, so `store.sentSnapshot(note, v)` for peers that reference A's newer upload returns `null` (`version != note.remoteVersion` → `ink.readSent` → nothing recorded), degrading every base that referenced it.

**What goes wrong:** no direct loss (other devices read the peer's file too), but A's file, its `seen` map and the bases other devices derive from it stay behind indefinitely.

**Confidence:** medium.

**Fix:** in the `changed.isEmpty()` branch also upload when `own != null && !sameContent(store.syncedSnapshot(note), store.withContent(note))` (or when `own.version != note.remoteVersion`).

## 6. A note whose PDF export fails is re-uploaded (and re-exported) on every single sync

**Where:** `SyncEngine.settle` / `SyncEngine.upload`

```kotlin
val catchUp = own != null && ((pdfExporter != null && note.remotePdfId == null && !note.locked) || needsSealing(note, own))
```
```kotlin
} else {
    pdfExporter?.let { export -> export(note)?.let { pdf -> ... } ?: note.remotePdfId }
}
```

`SyncManager` always passes `::exportPdf`. `exportPdf` returns `null` on any exception (it is deliberately swallowed: *"A failed PDF copy is logged and skipped"*). Then `pdfId` stays `null`, `markSynced(remotePdfId = null)` stores `null`, and the next sync's `catchUp` is true again.

**Concrete sequence:** a note contains a picture the exporter can't decode → every 60 s (`startAutoSync`) the app re-encodes the whole note, re-packs it (`NoteFile.toCloud`), re-uploads it, and rewrites `synced`/`sent` files. On WebDAV (ETags change on every PUT) every other device then sees a "changed" peer, re-merges, and rewrites all its page files (`InkSerializer.decode` produces fresh stroke objects, so `InkStore.save`'s identity cache misses).

**What goes wrong:** continuous battery/network/IO churn, no data loss.

**Fix:** remember the failure (e.g. store `remotePdfId = ""`/"skip" plus the note's `rev`) so `catchUp` isn't retried until the note changes.

## 7. `loadFirstPage` crashes on a manifest with no pages

**Where:** `InkStore.loadFirstPage`

```kotlin
val doc = readManifest(noteId) ?: return@locked null
val first = doc.pages.first()
```

`NoteMerger.merge` guards this exact case (`pages.ifEmpty { listOf(InkPage()) }`), which shows empty page lists are reachable. A cloud note file with `"pages":[]` (a corrupted file, a file written by an older version, or a hand-edited file in the shared folder — cloud input is explicitly untrusted here, and `NoteFile.decode` only validates the id) is stored via `insertFromCloud`, and from then on `loadThumbnail` throws for that note every time the home page loads it.

**Confidence:** medium (the crash is certain *if* such a manifest exists; I can't see `InkSerializer`/`InkDocument` to prove it can be produced by this version).

**Fix:** `val first = doc.pages.firstOrNull() ?: return@locked doc` and make `save`/`decode` normalise an empty page list.

## 8. Memory: a merge holds every peer's snapshot plus 3 decoded documents plus the re-encoded one

**Where:** `SyncEngine.settle` / `readNote`

```kotlin
var result = store.withContent(note)          // ink string #1
...
for ((device, file) in changed) {
    val read = readNote(file, note.id)         // ink string #2, plus `snapshot` (compressed) kept in `merges`
    result = NoteMerger.merge(base, ..., read.note, ...)   // decodes base + local + remote
    merges += Triple(device, file.version, read.snapshot)
}
```
`NoteMerger.merge` decodes three docs and encodes the result, while `store.syncedSnapshot`/`peerSnapshot` return further full text copies. The code is otherwise built for big notes (`InkStore` per-page files, "Android can't read rows over about 2 MB", `writeSnapshot` "Written in pieces: a long note's text is never copied whole into bytes") — the merge path is the exception: for a 20 MB ink with three peers you can hold on the order of 100+ MB of strings/arrays at once.

**What goes wrong:** `OutOfMemoryError` during sync; if it happens inside `InkStore.save`, `writeAtomically` keeps the old files (good), but the sync fails and retries, so the note never converges on that device.

**Confidence:** medium (needs a big note with several peers; no correctness bug).

**Fix:** merge page-by-page (decode only page i of each side, encode into a stream), and stream each peer snapshot to `peers/` as soon as it is read instead of collecting `merges`.

## 9. Untrusted cloud: the decompression limit is applied to a value that is then doubled into a `String`

**Where:** `NoteFile.fromCloud` + `readLimited`

```kotlin
if (isGzip(bytes)) java.util.zip.GZIPInputStream(bytes.inputStream(), 64 * 1024).readLimited().decodeToString()
```
`readLimited` caps the **decompressed** size at `MAX_DOWNLOAD_BYTES = 256 MB`, then `decodeToString()` turns it into a UTF-16 `String` (~512 MB) and `NoteFile.decode` copies the `ink` value again. A ~1 MB gzip file in the shared folder is enough.

**What goes wrong:** `OutOfMemoryError` (not an `Exception`, so the `runCatching` error reporting doesn't help) while syncing; also a cheap way for anyone with write access to the folder to make the app unopenable.

**Confidence:** medium (the numbers are from the code; OOM depends on the device).

**Fix:** read with a small limit for *text* (a few tens of MB), and/or decode the ink with a streaming reader into the `InkStore` instead of materialising the whole note as one `String`.

## 10. `commonBase` builds the base from a `HashMap`-ordered map → the union order, and thus the base, can differ per device

**Where:** `SyncEngine.commonBase`

```kotlin
for ((other, version) in seen) { ... base = base?.let { NoteMerger.union(it, next) } ?: next }
```

`seen` is a `HashMap` filled by `NoteFile.decode` in the order the file listed the entries, which is `store.peerVersions(...)` order (a directory listing). `NoteMerger.union` is order-sensitive (`merge(null, first(MAX), second)` keeps *first*'s order), and the `base` feeds `pick`/`mergeById`, so two devices can compute different bases for the same file and end up with different merged content.

**What goes wrong:** divergence that the `sameContent`/`behind` check can't always stop, i.e. repeated re-uploads; I could not construct a guaranteed infinite ping-pong, so treat this as a risk rather than a proven loop.

**Confidence:** low–medium.

**Fix:** iterate `seen` in sorted key order (and sort in `encodeTo` too), so every device builds the same union in the same order.

## Minor / lower severity

- **`SyncEngine.sync`**: `keys?.let { syncLockFile(it, listed) }` is outside any `runCatching` — a transient failure downloading/uploading the lock file aborts the entire sync instead of being collected into `SyncResult.errors`.
- **`NoteRepository.purge` vs. `markSynced`**: `purge` deletes the note's directory, but a concurrently finishing `markSynced` calls `ink.writeCompressedSnapshot`/`recordSent`, which do `dir(noteId).mkdirs()` — an orphaned `<root>/<noteId>/` can be recreated after the note is gone and never cleaned.
- **`NoteRepository.fillPhotoRequest`**: `dao.markEdited(noteId, note.title, ...)` uses the title read before the download/store, so a rename made meanwhile is reverted.
- **Merged `remotePdfId` is never persisted** (`replaceIfUnchanged` doesn't write it), so `catchUp` fires once for a note that only another device made a PDF for, and `upload` creates a *new* same-named PDF file (Drive allows duplicate names).
- **`InkStore.locks`** keeps one `Mutex` per note id forever — a slow leak (not a data bug).
